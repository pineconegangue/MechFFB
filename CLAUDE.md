## Build Commands

```powershell
# Build entire solution
dotnet build MechFFB.sln

# Build in Release mode
dotnet build MechFFB.sln -c Release

# Run the UI application
dotnet run --project MechFFBUI

# Build a specific project
dotnet build MechFFBEngine
dotnet build MechFFBReader
dotnet build MechFFBUI
```

There are no automated tests in this project.

## Architecture Overview

MechFFB is a MechWarrior 5 Mercenaries force feedback (FFB) application for DirectInput joysticks/wheels. It reads game telemetry from a shared memory region and translates game events into haptic effects.

### Project Structure

Three projects with a strict dependency chain: `MechFFBUI` → `MechFFBEngine` → `MechFFBReader`

**MechFFBReader** — Game telemetry ingestion (no UI dependency)
- `Infrastructure/MemoryMappedFileHandler.cs` — Opens the `"MechShakerBridgeMemory"` MMF created by the MechShakerBridge game mod. Reads a circular buffer (128 × 32-byte `EventData` entries) using a `ControlBlock` with `WriteIndex` and `PacketNumber` to detect new entries since the last poll.
- `TelemetryReader.cs` — Background thread that polls the MMF at 1ms intervals (adaptive: `Thread.Sleep(0)` if events found, `Thread.Sleep(1)` if idle). Raises typed events (`OnWeaponFire`, `OnDamage`, `OnMovement`, `OnJumpJet`, `OnImpact`). Has its own async log queue to keep `Console.WriteLine` off the hot read path.
- `Events/` — Typed event classes: `WeaponFireEvent`, `DamageEvent`, `MovementEvent`, `JumpJetEvent`, `ImpactEvent`.

**MechFFBEngine** — FFB logic and DirectInput output
- `FFBEngine.cs` — The core coordinator. Subscribes to `TelemetryReader` events and drives two optimization layers:
  - **Phase 1 (dedicated FFB thread)**: All `_hapticManager` calls are routed through `_effectQueue` (a `Channel<Action>`) and drained on a single `LongRunning` task. This prevents DirectInput COM calls from blocking the read thread.
  - **Phase 2 (batching)**: Events are accumulated in 10ms windows keyed by `BatchKey(Kind, SubType, Direction)`. Multiple events of the same type within the window are merged into one DirectInput effect, with magnitude scaled by a compressive curve (`2 - 1/N^0.6`). Damage-received batches use a quadratic formula on total damage so that LBX/10 (10×1dmg) feels identical to AC/10 (1×10dmg).
  - **Continuous singleton effects** (machine guns, lasers, jump jets, laser damage) bypass batching — each is owned by a single tracked effect ID.
- `Haptic/DirectInputHapticManager.cs` — Wraps SharpDX/DirectInput. Enumerates all devices including those without the `ForceFeedback` flag. Creates `ConstantForce` effects (impacts/recoil) and `Sine` periodic effects (rumble/vibration). Manages cooperative level (exclusive by default when a window handle is provided; non-exclusive if `DisableExclusiveMode` is set). Internally maps magnitude from `[0, 32767]` to DirectInput's `[0, 10000]` scale.
- `Haptic/DirectInputFFB.cs` — Static GUIDs for DirectInput effect types and unit conversion helpers.
- `Configuration/FFBConfiguration.cs` — JSON-serialized settings at `%AppData%\MechFFB\settings.json`. Two tiers: `SimpleModeSettings` (per-weapon-class intensity floats, 0–1 range) and `AdvancedModeSettings` (per-effect duration/attack/fade/frequency in ms and Hz). `MasterIntensity` multiplies all final magnitudes.
- `Configuration/WeaponProfiles.cs` — Per-weapon ballistic recoil profile lookup. The game's raw per-shot impulse (telemetry `F5`) is an unreliable proxy for weapon "feel", so `CalculateRecoilMagnitude` substitutes a *canonical* impulse from this table before running the (unchanged) recoil formula. Loaded at startup by layering `weapon_profiles.json` (vanilla) then `weapon_profiles.mods.json` (modded, e.g. YAWCE), each preferring a `%AppData%\MechFFB` override over the copy shipped next to the app (csproj `CopyToOutputDirectory`). Lookup key is the **quirk-stable** signature `(F0 shots, F2 pellets, F5 impulse)` via an allocation-free `record struct`; a missing profile falls back to the raw impulse. The JSON tables are regenerated by a Python script from `ProjectileWeaponStats.csv` (vanilla) / `YAWCE_AllProjectileWeapons.json` (mod) in the repo root.

**MechFFBUI** — WPF front-end (`net8.0-windows`)
- `Views/MainWindow.xaml.cs` — Single-window app. Hosts `FFBEngine`, redirects `Console.WriteLine` to an in-window debug log (capped at 250 lines). Slider changes are debounced 500ms before writing to `FFBConfiguration`. The window HWND is passed to `FFBEngine.SetWindowHandle()` after load to enable exclusive cooperative level.

### Key Invariants

- **All DirectInput calls must go through `EnqueueEffect()`** — never call `_hapticManager` directly from event handlers or timers. Violating this breaks the threading model.
- **Batch flush fires on the `System.Threading.Timer` thread** — the `_batchLock` protects `_pendingBatches`. After `FlushBatch` removes the entry, it calls `EnqueueEffect` (non-blocking).
- **`DestroyEffect` does not call `StopEffect` first** — calling `Stop()` before `Dispose()` can pause the device's FF output and silence the next effect. Effects auto-stop on dispose.
- **`_activeLaserDamageEffectId` uses `LASER_DAMAGE_PENDING = int.MaxValue` as a sentinel** — set immediately on the read thread before `EnqueueEffect` to prevent a second simultaneous damage tick from creating a duplicate effect.
- **Direction in centidegrees** — all direction values are stored and passed in centidegrees (0–35999). The game's convention (Rear=0°, Left=90°, Front=180°, Right=270°) is remapped in `HandleDamage`. Damage direction is bucketed to the nearest 45° sector (`BucketDirection`) so nearby-angle hits from the same attack merge in the batch.

### Ballistic recoil magnitude (`CalculateRecoilMagnitude`)

- **Two paths, selected by `F0>1 && F1>0`** (NumberOfShots & DelayBetweenShots). Single-shot: `mag = 257.18 · impulse^0.5588` (AC/2 700→10001 … AC/20 5000→30006). Burst: the per-shot impulse is remapped through `523.34 · 7.1429^t`, `t=(impulse−350)/150`, giving ~85% of the class single-shot magnitude *per kick*, with `F0` kicks scheduled at `F1` spacing. Both paths and the burst timing are intentional — do not collapse them.
- **The impulse fed in is the canonical value from `WeaponProfiles`**, not the raw telemetry impulse. Burst weapons store an in-band canonical (350/400/450/500); single weapons store 700/1250/2500/5000 (Gauss 4150). This is what keeps outliers from breaking the math.
- **Do NOT key the profile lookup on projectile speed (`F3`)** — live telemetry scales speed by the pilot's velocity skills/quirks (×1.125, ×1.219 observed), so an exact speed match fails. Speed is only a *nearest-base-≤-live* tie-break for the few keys shared by distinct weapons (MediumRifle vs Gauss; the Clan LBX solid-slugs).
- **Two overflow guards keep any weapon safe** (incl. unaccounted modded ones): the burst input is `Math.Clamp`ed to `[350,500]` before the exponential, and the final magnitude is clamped in float space *before* the int cast — `float.IsNaN(b) ? 0 : (int)Math.Clamp(b, 0f, 32767f)`. The float-space clamp is mandatory: this runtime's `(int)` of an out-of-range float wraps to `int.MinValue` (→ 0 after clamp), which was the original "silent burst weapon" bug.

### External Dependency

MechShakerBridge is a MechWarrior 5 game mod (not in this repo) that writes telemetry into the `"MechShakerBridgeMemory"` named MMF. Without MW5 running with this mod, `TelemetryReader` will poll and retry every 1 second indefinitely — this is normal behavior.

### NuGet Packages

- `SharpDX 4.2.0` + `SharpDX.DirectInput 4.2.0` — DirectInput FFB wrapper (MechFFBEngine)
- `System.IO.MemoryMappedFiles 4.3.0` — MMF access (MechFFBReader)
